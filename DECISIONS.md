## [chat-privacy]
- [chat-privacy] DECISION: Guests get no table access at all. The widget goes through three SECURITY DEFINER RPCs that take the conversation uuid: start_chat(p_page) -> uuid, send_chat_message(p_conversation, p_body, p_sender default 'user') -> message uuid, get_chat(p_conversation, p_after default null) -> jsonb array or null. "Owned" = the thread has user_id null (uuid is the secret) or user_id = auth.uid(). Execute granted to anon, authenticated; revoked from public. (affects: CHAT-PRIVACY.sql, components/ChatWidget.js)
- [chat-privacy] DECISION: RPCs for writes too, not a tightened insert policy: a policy check on "conversation exists and is mine" would need a definer helper anyway (guests can no longer SELECT conversations), and start_chat must return the new id, which insert ... returning cannot do without SELECT. All non-admin insert policies on both chat tables are dropped. (affects: CHAT-PRIVACY.sql)
- [chat-privacy] DECISION: start_chat stamps user_id = auth.uid() and takes display_name/email from profiles/auth.users itself; the browser no longer sends them, so a thread cannot be opened in someone else's name. Side effect: a signed-in visitor can no longer open a user_id-null thread, so their threads count toward the 5/hour per-account cap rather than the shared guest cap. (affects: CHAT-PRIVACY.sql, components/ChatWidget.js)
- [chat-privacy] DECISION: A thread opened while signed in is readable/writable only with that account's session; the uuid alone is not enough. After sign-out the widget gets null from get_chat, forgets the stored id and starts a fresh guest thread on the next message (good for shared computers). (affects: components/ChatWidget.js)
- [chat-privacy] DECISION: Not-found, expired and not-yours all look the same (get_chat -> null, send -> error 'chat_not_found', SQLSTATE P0002), so the API does not reveal whether a uuid exists. The widget retries a visitor message once in a new thread on chat_not_found; the stored auto-reply never retries. (affects: CHAT-PRIVACY.sql, components/ChatWidget.js)
- [chat-privacy] DECISION: Rate limits still apply. SECURITY DEFINER switches current_user only; the 'role' GUC PostgREST set (anon/authenticated) and request.jwt.claims are unchanged inside the call, and the RPCs set only search_path, so rate_limited_caller() sees the browser caller exactly as for a direct insert. RATE-LIMITS.sql untouched. Not verified against the live DB (no SQL run). (affects: RATE-LIMITS.sql triggers)
- [chat-privacy] DECISION: Signed-in owners also get SELECT policies on their own rows ("owner reads conversation" / "owner reads messages", to authenticated). Nothing in the app uses them today; they keep direct reads and realtime correct for owners. Admin policies (is_admin ALL) unchanged, so /chat, its replies and its realtime feed are untouched; app/chat/page.js not edited. (affects: CHAT-PRIVACY.sql)
- [chat-privacy] DECISION: Widget realtime subscription removed (RLS now hides rows from a guest's postgres_changes feed). Polling get_chat replaces it: every 4 s while the panel is open, every 15 s while closed (feeds the badge), only while the tab is visible, and only for messages from the newest one seen minus a 60 s overlap (deduped by id), so a long thread is not re-sent each tick. (affects: components/ChatWidget.js)
- [chat-privacy] DECISION: The same chat block (RPCs + policies) replaces the old policy block in supabase-schema.sql and RUN-THIS-IN-SUPABASE.sql, and both drop the old leaky policy names, so re-running them cannot reopen the leak. The three copies must be kept in step. (affects: supabase-schema.sql, RUN-THIS-IN-SUPABASE.sql)
- [chat-privacy] DECISION: CHAT-PRIVACY.sql is split into PART A (functions only, old widget unaffected) and PART B (policy swap). Run all then deploy, or A -> deploy -> B for no gap. (affects: CHAT-PRIVACY.sql)
